## Decisiones de implementación

Se continúa la solución existente, con un proyecto compartido `AceriaApp.Observabilidad` para componentes ASP.NET e integración de observabilidad. Se mantienen los cuatro catálogos originales y sus proyectos de tests; sus tests funcionales se añaden a los proyectos del punto. Es una decisión de implementación para evitar duplicar middleware entre Producción e Inventario. No se despliega una plataforma externa de observabilidad: consola JSON permite inspeccionar eventos reales sin añadir servicios ajenos al temario.

### 7.1 Logging

Serilog.AspNetCore 8.0.3, consola JSON y propiedades estructuradas. CorrelationId validado (1–64 caracteres ASCII alfanuméricos, guion y subrayado); un valor inválido se sustituye por un identificador generado. La respuesta incluye X-Correlation-ID y las llamadas HTTP a Inventario propagan el mismo valor. Los logs llevan servicio, CorrelationId, TraceId, método, plantilla de ruta, estado y duración. Los eventos nuevos propios de M7 (resumen HTTP, manejador de excepciones y callbacks de resiliencia) no registran cuerpos, query strings, Authorization ni valores libres de excepciones. Se elimina también RequestPath, incorporado por los scopes de ASP.NET, y la cabecera de correlación se repone con OnStarting tras un error. Esta garantía no supone una auditoría de todos los logs heredados de workers M6 o EF; sus errores pueden contener detalles internos y requieren control de acceso y revisión antes de uso productivo. Se reducen los logs automáticos de framework/HTTP/EF que podrían duplicar datos de petición. Los logs de eventos conservan EventoId/OrdenId donde proceda; no se afirma tracing distribuido completo ni exportación a un backend externo.

### 7.2 Health Checks

`/health/live` comprueba el proceso y no consulta dependencias. `/health/ready` comprueba SQL Server mediante consultas reales y RabbitMQ cuando los workers están habilitados. La respuesta pública solo contiene estado, nombres de componentes y duración, sin credenciales, excepciones o cadenas de conexión. SQL y AMQP tienen límites de espera y respetan cancelación. Se mantiene la ruta heredada `/health` de Inventario. Readiness acredita acceso a dependencias, no vaciado del outbox ni finalización de todos los consumidores.

### 7.3 Excepciones

IExceptionHandler y ProblemDetails de ASP.NET Core 8 para fallos inesperados, con título público genérico, status 500 y correlación. Los errores esperados de Result mantienen sus 400/404/409/422; la indisponibilidad remota sigue siendo 503. Cancelación de la petición no se convierte en 500 y una respuesta ya iniciada no se reescribe. Un endpoint de fallo controlado existe únicamente con entorno Development y una opción de diagnóstico activada; no queda disponible en Production.

### 7.4 Resiliencia

Polly v8 mediante Microsoft.Extensions.Http.Resilience compatible con .NET 8, versión fijada tras comprobación de restauración. Se aplica únicamente al cliente de consulta de Inventario. Orden: timeout total de 6 s, retry (máximo 2 reintentos, 200 ms iniciales exponenciales con jitter), circuito (4 muestras mínimas, proporción de fallos 0,5 en ventana de 10 s, apertura 5 s), timeout de intento de 1 s. HTTP 408/429/5xx, errores de transporte y timeout de intento son transitorios; 400/401/403/404 y cancelación del usuario no se reintentan. No se reintentan métodos mutantes. Un circuito abierto y el timeout agotado se traducen a indisponibilidad, nunca a éxito ficticio. El estado se comparte por cliente/destino, no se reconstruye por llamada. Las pruebas de tiempo usan reloj controlado o señales observables; no dependen de sleeps largos.

## Alternativas consideradas

Conservar solo catálogos no acredita observabilidad ni resiliencia en ejecución. Instrumentar las dos API por separado duplicaría lógica y pruebas. Se adopta la biblioteca compartida y una política de lectura HTTP acotada, manteniendo puertos y dominio independientes. Las decisiones siguen el alcance ya autorizado; no requieren nuevas decisiones de producto del usuario.
